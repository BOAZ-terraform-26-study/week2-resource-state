## 오늘의 의존성 지도

Week1에서는 명령의 흐름(Scope → Author → Initialize → Plan → Apply)을 따라갔습니다.
오늘은 리소스 사이의 의존 관계를 따라갑니다.

이 의존성 지도를 오늘 세 번 사용합니다. Block A에서 잇고, Block B에서 apply 로그와 대조하고, Block C에서 뒤집습니다.

```
0층 · 먼저 AWS에서 조회하는 것 (plan 때 이미 결과를 받아둡니다)
     data.aws_ami.al2023                 data.aws_availability_zones.available

1층 · 아무도 안 기다리는 유일한 리소스
     aws_vpc.main

2층 · VPC만 있으면 되는 셋 → 동시에 시작
     aws_subnet.public             ← ① vpc      ← ② AZ데이터
     aws_internet_gateway.gw       ← ③ vpc
     aws_security_group.web        ← ⑧ vpc

3층 · 2층이 끝나야 시작 → 둘이 동시에
     aws_route_table.public        ← ④ vpc      ← ⑤ igw
     aws_instance.web              ← ⑨ subnet   ← ⑩ sg      ← ⑪ ami데이터

4층 · 맨 마지막
     aws_route_table_association.public   ← ⑥ subnet   ← ⑦ route_table
```

참조 번호와 뜻은 개념워크북 1번 표와 같습니다.

> [!NOTE]
> `←`는 "이 값을 기다린다"는 뜻입니다. 그래서 나중에 `terraform graph`를 돌리면 `aws_subnet.public -> aws_vpc.main`(서브넷이 VPC를 기다린다)로 똑같은 방향이 나옵니다. 지도와 graph의 방향을 통일해 뒀으니 헷갈릴 일이 없습니다.
>
> 그리고 위에서 아래로 내려갈수록 나중에 만들어집니다. 0층이 가장 먼저, 4층이 가장 마지막입니다.

| 스텝 | 여기서 잇는 참조 | 하는 일 |
|------|------------------|--------|
| A-3 | ① ② | 서브넷 작성 |
| A-4 | ③ ④ ⑤ ⑥ ⑦ | IGW · 라우트 테이블 · 연결 작성 |
| A-5 | - | plan. `Plan: 5 to add` |
| A-6 | - | **네트워크 5개 apply** |
| B-1 | ⑧ ⑨ ⑩ ⑪ | SG · EC2 작성 |
| B-2 | - | plan. `Plan: 2 to add` |
| B-3 | - | **컴퓨트 2개 apply** |
| C-1 · C-2 | 전부 **역방향** | **7개 destroy** (리프 노드부터) |

> [!NOTE]
> 길을 잃었을 때는 "지금 몇 번 참조를 잇는 중이지?"만 확인하면 됩니다.
> 오늘 배울 것을 한 문장으로 줄이면, 참조를 다 이으면 순서는 적지 않아도 된다는 것입니다.

> [!TIP]
> 4층이 EC2가 아닙니다. 인자가 참조 두 줄뿐인 `route_table_association`이 가장 마지막입니다. 왜 그런지는 B-3에서 로그로 확인합니다.

오늘 나올 숫자를 미리 정리해 둡니다. 이것과 다르면 문제가 있는 것입니다.

| 지점 | 나와야 하는 숫자 |
|------|------|
| A-5 plan (네트워크만) | `Plan: 5 to add, 0 to change, 0 to destroy.` |
| A-6 후 `state list` | **7줄** (리소스 5 + 데이터 소스 2) |
| B-2 plan (EC2 추가) | `Plan: 2 to add, 0 to change, 0 to destroy.` |
| B-4 `state list` | **9줄** (리소스 7 + 데이터 소스 2) |
| C-1 destroy plan | `Plan: 0 to add, 0 to change, 7 to destroy.` |
| C-2 완료 | `Destroy complete! Resources: 7 destroyed.` |

> [!NOTE]
> `7`이 세 군데 나오는데 뜻이 다 다릅니다. 헷갈리지 않게 미리 구분해 둡니다.
> - 오늘 만드는 리소스 7개 (데이터 소스 제외)
> - A-6 후 `state list`의 7줄 (그때까지 만든 리소스 5개 + 데이터 소스 2개)
> - destroy되는 7개 (첫 번째와 같은 7)

> macOS는 `brew install jq`, Ubuntu/WSL은 `sudo apt install -y jq`. 설치가 안 되어도 실습은 진행할 수 있지만 B-4에서 결과 확인이 불편해집니다.

Week1은 `main.tf` 하나였는데 오늘은 `network.tf`와 `compute.tf`로 나뉘어 있습니다. 왜일까요?

Terraform은 파일 경계를 구분하지 않습니다. 현재 폴더의 `.tf` 파일을 전부 읽어서 하나로 합칩니다(Week1 A-2). 그래서 파일을 쪼개는 기준은 문법이 아니라 사람이 찾기 편한 단위입니다.

즉 `network.tf`에 있는 `aws_vpc.main`을 `compute.tf`에서 바로 참조할 수 있습니다. 파일이 달라도 Terraform에게는 같은 코드입니다.

> [!WARNING]
> 터미널은 하나만 쓰세요. 두 개에서 동시에 명령을 돌리면 `Error acquiring the state lock` 에러가 납니다. Terraform이 state를 두 명이 동시에 고치는 것을 막기 때문입니다.

### [실습] A-2. 내 값 채우기: `project_name` · `my_ip`

```bash
cp example.tfvars terraform.tfvars
curl -4 ifconfig.me            # 내 공인 IPv4 주소 한 줄이 나옵니다
```

> [!NOTE]
> `terraform.tfvars`는 변수의 실제 값을 적어두는 파일입니다. Terraform이 자동으로 읽어갑니다. 사람마다 값이 다르고(내 IP가 들어가니까) 비밀이라서 커밋하지 않습니다(`.gitignore`에 있습니다).

`terraform.tfvars`를 열어서 두 값을 바꿉니다.

```hcl
region        = "ap-northeast-2"
project_name  = "boaz26-w2-{본인-github-id}"   # 예: boaz26-w2-kdh1834
my_ip         = "1.2.3.4"                      # curl -4 결과. /32 를 붙이지 마세요
instance_type = "t3.micro"
```

> [!IMPORTANT]
> `my_ip`에 `/32`를 붙이지 마세요. 코드 쪽에서 `"${var.my_ip}/32"`로 자동 조립합니다. `1.2.3.4/32`를 넣으면 `1.2.3.4/32/32`가 되어버립니다.
>
> 실수하면 `variables.tf`가 값을 검사해 차단합니다. 값이 `CHANGE-ME`거나 형식이 틀리면 plan이 아예 시작되지 않습니다.
>
> ```
> Error: Invalid value for variable
>   my_ip는 1.2.3.4 처럼 순수 IPv4여야 합니다. /32나 CIDR을 넣지 마세요.
> ```
>
> 이 실패는 미리 발견되는 편이 낫습니다. 이 검사가 없으면 SG를 만드는 순간(= apply 도중)에 `InvalidParameterValue`로 실패합니다. 그때는 VPC, 서브넷, IGW가 이미 만들어져 있어서 복구가 가장 번거로운 시점입니다.

> [!TIP]
> `curl`에 `-4`를 꼭 붙이세요. 안 붙이면 IPv6 주소(`2001:...`)가 나올 수 있는데, 그건 `/32`를 붙일 수 없는 형식입니다.

> [!IMPORTANT]
> **CP1.** Discord에 `project_name` 한 줄만 올려주세요. apply 전에 오타를 확인합니다.

> [!CAUTION]
> `my_ip` 값은 Discord에 올리지 마세요. 본인 공인 IP입니다.
> `curl -4 ifconfig.me`가 IPv4 한 줄을 출력했는지 여부만(`OK` / `실패`) 보고하세요.

### [실습] A-3. 첫 참조 ① ②: 서브넷 만들기

지금 하는 일은 VPC 안에 서버가 배치될 서브넷을 하나 만드는 것입니다.

`network.tf`의 첫 TODO입니다. `data "aws_availability_zones"`와 `aws_vpc.main`은 이미 채워져 있습니다.

```hcl
resource "aws_subnet" "public" {
  vpc_id            = aws_vpc.main.id                                # 참조 ①
  cidr_block        = "10.0.1.0/24"
  availability_zone = data.aws_availability_zones.available.names[0] # 참조 ②

  map_public_ip_on_launch = true

  tags = { Name = "${var.project_name}-public" }
}
```

한 줄씩 읽어봅시다.

| 줄 | 무슨 뜻인가 |
|----|-----------|
| `vpc_id = aws_vpc.main.id` | "이 서브넷은 저 VPC 안에 있습니다". **참조 ①** |
| `cidr_block = "10.0.1.0/24"` | 이 서브넷이 쓸 주소 범위. `10.0.1.무엇` 256개 (개념워크북 0-3) |
| `availability_zone = ...names[0]` | AWS에서 조회한 AZ 목록 중 첫 번째. **참조 ②** |
| `map_public_ip_on_launch = true` | 이 서브넷에서 뜨는 서버에 퍼블릭 IP를 자동으로 붙여준다 |
| `tags = { Name = ... }` | 콘솔에서 식별할 이름 |

읽는 규칙은 하나입니다. 왼쪽은 인자 이름(provider가 정함), 오른쪽은 참조(내가 씀).

```
vpc_id = aws_vpc.main.id
   ^          ^
   |          +--- 오른쪽: 내가 붙인 주소(aws_vpc.main) + 속성(.id)
   +-------------- 왼쪽: aws_subnet 이 요구하는 인자 이름 (못 바꿈)
```

여기서 세 가지를 확인합니다.

**(1) AZ를 하드코딩하지 않습니다.** `"ap-northeast-2a"`라고 직접 적는 대신 AWS에서 조회합니다. AZ 이름이 계정마다 다른 데이터센터에 붙기 때문이고, AZ마다 쓸 수 있는 인스턴스 타입도 다르기 때문입니다. 자세한 이유는 개념워크북 7번에 있습니다.

**(2) `map_public_ip_on_launch = true` 한 줄이 퍼블릭 IP가 붙는 원인입니다.** 이 서브넷에서 뜨는 서버는 퍼블릭 IPv4를 자동으로 받습니다. 그래서 우리는 Elastic IP를 만들지 않습니다. EIP는 안 쓰고 있어도 시간당 과금됩니다.

**(3) 방금 개념워크북 0-5의 세 조건 중 첫 번째를 만들었습니다.** 나머지 둘이 어느 스텝인지만 확인하고 넘어가세요.

```
① 퍼블릭 IP가 있는가    : map_public_ip_on_launch = true            <- A-3 (방금 완료)
② 인터넷 경로가 있는가  : IGW + 라우트 테이블 0.0.0.0/0 + 연결      <- A-4 (다음)
③ 방화벽이 허용하는가   : SG의 egress 전체 허용                     <- B-1
```

### [실습] A-4. 참조 ③ ④ ⑤ ⑥ ⑦: IGW · 라우트 테이블 · 연결

지금 하는 일은 인터넷 게이트웨이(IGW)를 만들고, 라우트 테이블에 인터넷으로 나가는 경로를 적고, 그 테이블을 아까 만든 서브넷에 연결하는 것입니다.

`network.tf`의 남은 TODO 3개를 채웁니다.

```hcl
resource "aws_internet_gateway" "gw" {
  vpc_id = aws_vpc.main.id # 참조 ③
  tags   = { Name = "${var.project_name}-igw" }
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id # 참조 ④

  route {
    cidr_block = "0.0.0.0/0"                # "어디로 가든" (= 인터넷 전체)
    gateway_id = aws_internet_gateway.gw.id # 이 IGW로 내보낸다 (참조 ⑤)
  }

  tags = { Name = "${var.project_name}-rt-public" }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id      # 어느 서브넷에 (참조 ⑥)
  route_table_id = aws_route_table.public.id # 어느 라우트 테이블을 (참조 ⑦)
}
```

그리고 `outputs.tf`의 첫 TODO도 지금 채웁니다.

```hcl
output "vpc_id" {
  description = "생성된 VPC ID"
  value       = aws_vpc.main.id
}
output "subnet_id" {
  description = "퍼블릭 서브넷 ID"
  value       = aws_subnet.public.id
}
output "subnet_az" {
  description = "서브넷이 놓인 AZ. data.aws_availability_zones 가 골라준 값"
  value       = aws_subnet.public.availability_zone
}
```

여기서 처음 보는 것이 두 개 있습니다.

**(1) `route`는 리소스가 아니라 인자입니다.**

`resource "aws_route_table"` 안에 중괄호로 들어간 `route { }`는 별개의 리소스가 아니라 라우트 테이블이 가진 속성입니다. 겉모습이 `resource` 블록과 비슷해서 헷갈리기 쉬운데, 앞에 `resource`라는 단어가 없으면 리소스가 아닙니다. 이렇게 블록 안에 들어가는 것을 인라인 블록이라고 부릅니다.

**(2) `association`은 연결하는 행위 자체가 리소스입니다.**

AWS 콘솔에는 이걸 위한 독립 화면이 없습니다(라우트 테이블 화면의 탭으로 보일 뿐입니다). 그런데 Terraform에서는 독립된 리소스 하나이고, 인자가 참조 두 줄뿐입니다. 그래서 의존성 지도에서 가장 마지막 층에 놓입니다. 서브넷과 라우트 테이블이 둘 다 만들어져야 비로소 만들 수 있으니까요.

### [실습] B-1. 참조 ⑧ ⑨ ⑩ ⑪: 시큐리티 그룹 + EC2

지금 하는 일은 서버 앞에 붙일 시큐리티 그룹(SG)을 만들고, 드디어 EC2 인스턴스를 띄우는 것입니다.

`compute.tf`의 TODO 2개를 채웁니다. `data "aws_ami"`는 이미 채워져 있습니다.

```hcl
resource "aws_security_group" "web" {
  name        = "${var.project_name}-web-sg"
  description = "boaz w2 lab: SSH from my IP only"
  vpc_id      = aws_vpc.main.id # 참조 ⑧

  ingress {                                   # 들어오는 것
    description = "SSH from my IP"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["${var.my_ip}/32"]         # 내 IP 하나만
  }

  egress {                                    # 나가는 것
    description = "all outbound"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"                        # -1 = 모든 프로토콜
    cidr_blocks = ["0.0.0.0/0"]               # 어디로든 나갈 수 있음
  }

  tags = { Name = "${var.project_name}-web-sg" }
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.al2023.id      # 참조 ⑪
  instance_type          = var.instance_type
  subnet_id              = aws_subnet.public.id        # 참조 ⑨
  vpc_security_group_ids = [aws_security_group.web.id] # 참조 ⑩

  root_block_device {                # 서버의 디스크
    volume_type           = "gp3"
    volume_size           = 8        # 8 GiB
    delete_on_termination = true     # 서버 지울 때 디스크도 같이 삭제
  }

  metadata_options {
    http_tokens = "required"         # 보안 설정. 오늘은 몰라도 됩니다 (아래 NOTE)
  }

  tags = { Name = "${var.project_name}-web" }
}
```

> [!NOTE]
> `root_block_device`와 `metadata_options`는 오늘 몰라도 됩니다. 앞의 것은 디스크 설정(8GiB짜리 SSD를 붙이고, 서버를 지울 때 같이 지운다), 뒤의 것은 켜두면 좋은 보안 기본값입니다. 실무에서 매번 쓰는 것들이라 미리 넣어뒀을 뿐, 오늘의 학습 목표(참조·그래프·state)와는 상관없습니다. 궁금하면 개념워크북 0-4의 EBS 항목을 보세요.

> [!NOTE]
> 시큐리티 그룹은 양방향 방화벽입니다. `ingress`(인그레스)는 들어오는 트래픽 규칙이고, 여기서는 "내 IP에서 오는 22번 포트(SSH)만 허용"입니다. `egress`(이그레스)는 나가는 트래픽 규칙이고, 여기서는 "어디로든 다 나갈 수 있음"입니다.
>
> 나가는 걸 열어두는 이유는 서버가 패키지를 받거나 업데이트할 수 있어야 하기 때문입니다. 개념워크북 0-5의 ③번 조건(방화벽이 허용하는가)이 이 `egress`입니다.

`outputs.tf`의 두 번째 TODO도 채웁니다.

```hcl
output "ami_id" {
  description = "data.aws_ami 가 찾아낸 AL2023 AMI ID"
  value       = data.aws_ami.al2023.id
}
output "instance_id" {
  description = "EC2 인스턴스 ID (destroy 전에 기록해 두면 증빙이 됩니다)"
  value       = aws_instance.web.id
}
output "instance_public_ip" {
  description = "자동 할당된 퍼블릭 IPv4. EIP가 아니라서 stop/start 하면 바뀝니다. Discord에 올리지 말 것"
  value       = aws_instance.web.public_ip
}
```

여기서 확인할 것은 다섯 가지입니다.

**(1) SG에 `vpc_id`를 빼먹으면 안 됩니다.** 빼면 SG가 기본 VPC에 만들어지고, EC2 생성 단계에서 이렇게 실패합니다.
```
Error: creating EC2 Instance: InvalidParameterValue:
  Security group sg-xxx and subnet subnet-yyy belong to different networks.
```
SG와 EC2가 서로 다른 VPC에 있다는 뜻입니다.

여기서 말하는 기본 VPC는 AWS 계정을 만들면 리전마다 미리 만들어져 있는 연습용 VPC입니다. `vpc_id`를 안 적으면 SG가 거기에 만들어지고, 우리가 만든 VPC와는 다른 네트워크가 되어버립니다.

**(2) `vpc_security_group_ids`는 리스트입니다.** SG는 서버 한 대에 여러 개 붙일 수 있어서, 하나만 붙여도 `[ ]`가 필요합니다.

**(3) `ami = data.aws_ami.al2023.id`가 오늘 유일한 `data.` 참조입니다.** 리소스는 `aws_subnet.public`처럼 바로 시작하지만, 데이터 소스는 앞에 `data.`가 붙습니다.

**(4) `cidr_blocks = ["0.0.0.0/0"]`로 22번을 열지 마세요.** 몇 분 안에 전 세계 스캔 트래픽이 붙습니다. 반드시 내 IP `/32`만.

**(5) `associate_public_ip_address`를 쓰지 마세요.** 퍼블릭 IP는 서브넷의 `map_public_ip_on_launch` 한 곳에서만 통제합니다. 두 군데에 적으면 나중에 어느 쪽이 실제로 적용되는지 헷갈리고, 이 값을 바꾸면 서버가 통째로 재생성(`-/+`)됩니다.

> [!CAUTION]
> 키페어를 만들지 마세요. 오늘은 SSH 접속을 하지 않습니다.
>
> 코드로 키를 만들면 비밀키가 tfstate에 평문으로 저장되고, `.pem` 파일이 실수로 커밋되는 사고가 발생할 수 있습니다.
>
> 그럼 SG에 22번 규칙은 왜 남기냐고요? ① 문법을 배우기 위해 ② B-5 drift 실습에서 사용하기 위해 ③ "필요한 만큼만 여는" 습관을 들이기 위해서입니다.

A-5와 비교해보세요. `subnet_id`가 `(known after apply)`가 아니라 확정된 값입니다.

서브넷은 A-6에서 이미 만들어졌고 state에 값이 적혀 있으니 Terraform이 그 값을 압니다. 참조 ⑨는 그대로 있지만, 가리키는 대상이 이미 존재하는 것이죠.

반면 `vpc_security_group_ids`는 아직 `(known after apply)`입니다. SG를 이번에 만들 거니까요(참조 ⑩).

> [!TIP]
> `ami_id` 값을 옆 사람과 비교해보세요. 같은 리전, 같은 필터라면 같은 값이 나옵니다. 데이터 소스는 같은 조건에 같은 결과를 반환하니까요.
>
> 다만 `most_recent = true`라서 다음 주에 돌리면 다른 값이 나올 수 있습니다. 그리고 `ami`는 `-/+`(교체) 속성입니다. 코드를 안 고쳤는데 EC2가 재생성될 수 있다는 뜻입니다(B-6에서 확인).

### [실습] B-4. state 분석 ⭐

apply는 리소스를 만드는 것으로 끝나지 않습니다. state에 기록하는 것까지 포함합니다. 그 state를 분석합니다.

> [!NOTE]
> 아래에 `jq`라는 명령이 나옵니다. JSON 파일에서 원하는 부분만 골라 보여주는 도구입니다. 없으면 `brew install jq`(macOS) / `sudo apt install jq`(Ubuntu)로 설치하세요. 없어도 `terraform state show`로 대부분 볼 수 있습니다.

#### ① 주소 목록 보기

```bash
terraform state list
```
```
data.aws_ami.al2023
data.aws_availability_zones.available
aws_instance.web
aws_internet_gateway.gw
aws_route_table.public
aws_route_table_association.public
aws_security_group.web
aws_subnet.public
aws_vpc.main
```

9줄 = 리소스 7 + 데이터 소스 2. `Plan: 5 to add` + `Plan: 2 to add` = 7과 딱 맞습니다.

#### ② 하나만 자세히 확인하기

```bash
terraform state show aws_instance.web
```

이 중에서 확인할 것: `id` · `private_ip` · `public_ip` · `subnet_id` · `ami` · `instance_state` · `tags` vs `tags_all`.

```bash
terraform state show aws_subnet.public | grep -E "availability_zone|cidr_block|map_public"
```

`availability_zone = "ap-northeast-2a"`. 데이터 소스가 선택한 값이 여기 저장돼 있습니다.

#### ③ 파일을 직접 열어보기: 최상위 키 7개

```bash
ls -la terraform.tfstate
jq 'keys' terraform.tfstate
jq '{version, terraform_version, serial, lineage}' terraform.tfstate
```
```json
{
  "version": 4,
  "terraform_version": "1.15.8",
  "serial": 3,
  "lineage": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

| 키 | 뜻 |
|----|-----|
| `version: 4` | state 파일의 포맷 버전. Terraform 버전이 아닙니다 |
| `serial` | state가 저장된 횟수. 저장할 때마다 늘어납니다 |
| `lineage` | 이 state의 고유 식별 번호. 다른 인프라의 state를 잘못 덮어쓰는 사고를 방지합니다 |

> [!IMPORTANT]
> `serial` 숫자는 사람마다 다르게 나옵니다. apply 횟수가 아니라 state를 저장한 횟수이기 때문입니다. apply 말고도 output이 바뀌거나 refresh 결과가 달라지면 저장이 한 번 더 일어납니다. 그래서 apply를 두 번 했는데 `serial`이 2가 아닐 수 있습니다.
>
> 이 번호는 Week3에서 활용됩니다. 같은 state를 두 사람이 각자 고쳤을 때 "내가 가진 것이 이전 버전이다"를 판단하는 근거가 이 숫자입니다.

#### ④ 리소스 목록과 속성

```bash
jq -r '.resources[] | "\(.mode)  \(.type).\(.name)"' terraform.tfstate
jq '.resources[] | select(.type=="aws_instance") | .instances[0].attributes
    | {id, ami, instance_type, subnet_id, private_ip, public_ip, tags, tags_all}' terraform.tfstate
```

> [!CAUTION]
> `attributes`에는 우리가 코드에 쓴 것보다 훨씬 많은 값이 들어 있습니다. AWS가 자동으로 정한 기본값까지 전부입니다.
>
> 그리고 plan이 `~`인지 `-/+`인지 계산하는 근거가 바로 이 값들입니다. 전부 평문입니다.

#### ⑤ ⭐ `dependencies`: 내가 적지 않은 그래프

```bash
jq -r '.resources[] | "\(.type).\(.name)  <-  \(.instances[0].dependencies // [] | join(", "))"' terraform.tfstate
```
```
aws_instance.web  <-  aws_security_group.web, aws_subnet.public, aws_vpc.main, data.aws_ami.al2023, ...
aws_internet_gateway.gw  <-  aws_vpc.main
aws_route_table.public  <-  aws_internet_gateway.gw, aws_vpc.main
aws_route_table_association.public  <-  aws_route_table.public, aws_subnet.public, aws_vpc.main, ...
aws_security_group.web  <-  aws_vpc.main
aws_subnet.public  <-  aws_vpc.main, data.aws_availability_zones.available
aws_vpc.main  <-
```

이어서 아래 명령의 출력과 나란히 비교해 보세요.

```bash
terraform graph | grep '\->' | sed 's/"//g; s/;//' | sort
```

> [!IMPORTANT]
> 왼쪽은 `.tf` 파일에서 계산한 그래프, 오른쪽은 state에 저장된 그래프입니다. 같습니다.
>
> 그런데 왜 state에 또 적어둘까요? `.tf` 파일을 다 지워버려도 `terraform destroy`가 올바른 순서로 동작해야 하기 때문입니다. 코드가 사라지면 참조도 사라지지만, state의 `dependencies`는 남습니다. C-2에서 삭제 순서가 지켜지는 근거가 바로 이것입니다.
>
> 저는 이 배열을 적은 적이 없습니다. 참조 ①~⑪에서 자동으로 추출되어 여기 적혔습니다.

> [!NOTE]
> 두 가지를 더 설명합니다.
>
> **(1) 목록이 참조 개수보다 많아 보입니다.** `dependencies`에는 직접 의존 외에 간접 의존까지 들어갑니다. association의 목록에 `aws_vpc.main`이 보이는 이유입니다(association → 서브넷 → VPC로 이어지니까요).
>
> **(2) `aws_instance.web`의 목록에 `aws_route_table_association.public`이 없습니다.** EC2는 인터넷 경로가 연결되기를 기다리지 않습니다. 참조가 없으니까요.
>
> 오늘은 문제가 안 되지만, 서버 부팅 스크립트로 패키지를 받는다면 인터넷이 아직 없어서 실패할 수 있습니다. 그때 필요한 것이 `depends_on`입니다(개념워크북 6번).

#### ⑥ 기계가 읽는 JSON으로 출력하기

```bash
terraform show -json | jq '.values.root_module.resources[] | {address, depends_on}'
terraform show -json > state.json     # 만들었으면 git status를 반드시 확인!
```

> [!CAUTION]
> `state.json`은 state와 같은 수준의 민감 정보입니다. `.gitignore`로 제외되어 있지만 직접 확인하세요.

#### ⑦ `state pull`

```bash

```

지금처럼 state가 내 노트북에 있을 때는 `cat terraform.tfstate`와 거의 같습니다. 이 명령이 실제로 의미가 있는 것은 Week3의 S3 원격 저장소입니다. 짝인 `state push`는 위험해서 오늘은 쓰지 않습니다.

### [실습] B-6 (심화 ⭐). `~` vs `-/+` 체험: plan만, apply 절대 금지

> [!WARNING]
> 이 스텝에서는 절대 `apply`를 누르지 마세요. plan만 보고 즉시 원래대로 되돌립니다. apply하면 EC2가 삭제되고 새로 만들어집니다(시간 낭비 + 과금).

#### 대조군: `instance_type`은 `~` (제자리 수정)

`terraform.tfvars`에서 `instance_type = "t2.micro"`로 바꾸고 plan.

```
  # aws_instance.web will be updated in-place
  ~ resource "aws_instance" "web" {
        id            = "i-0123456789abcdef0"
      ~ instance_type = "t3.micro" -> "t2.micro"
    }

Plan: 0 to add, 1 to change, 0 to destroy.
```

EC2에는 인스턴스 타입을 바꾸는 API가 있어서 중지 → 변경 → 시작으로 처리됩니다. 인스턴스 ID가 유지되므로 `~`입니다.

하지만 서버는 잠깐 멈춥니다. `~`가 곧 "무해"는 아닙니다.

#### 본 실습: 서브넷 `cidr_block`은 `-/+`, 그리고 연쇄 교체

`network.tf`에서 `cidr_block = "10.0.1.0/24"` → `"10.0.2.0/24"` (숫자 한 글자) 로 바꾸고 plan.

```
Resource actions are indicated with the following symbols:
-/+ destroy and then create replacement

  # aws_instance.web must be replaced
-/+ resource "aws_instance" "web" {
      ~ subnet_id = "subnet-0a1b2c3d4e5f67890" -> (known after apply) # forces replacement
    }

  # aws_route_table_association.public must be replaced
-/+ resource "aws_route_table_association" "public" {
      ~ subnet_id = "subnet-0a1b2c3d4e5f67890" -> (known after apply) # forces replacement
    }

  # aws_subnet.public must be replaced
-/+ resource "aws_subnet" "public" {
      ~ cidr_block = "10.0.1.0/24" -> "10.0.2.0/24" # forces replacement
    }

Plan: 3 to add, 0 to change, 3 to destroy.
```

세 가지를 읽으세요.

**(1) `# forces replacement` 주석의 위치.** 리소스 헤더가 아니라 원인이 된 속성 줄의 맨 끝입니다. 그 속성이 교체의 원인입니다.

**(2) 연쇄 교체.** 한 줄 고쳤는데 3개가 재생성됩니다. 서브넷이 삭제되면 그 `id`를 참조하던 association과 EC2도 같이 삭제됩니다. 의존성 지도가 곧 교체가 전파되는 경로입니다.

**(3) `(known after apply)`의 재등장.** "새 서브넷의 id를 아직 모른다 → 그걸 참조하는 서버를 새로 만들어야 한다"는 인과가 이 한 줄에 다 들어 있습니다.

apply를 누르면 EC2가 삭제되고 퍼블릭 IP가 바뀝니다. 운영 중인 서비스였다면 장애입니다.

#### 반드시 원래대로 되돌리기

> [!CAUTION]
> `git checkout -- network.tf` / `git restore network.tf` 를 쓰지 마세요.
>

### [실습] B-7 (심화 ⭐⭐). cycle(고리) 만들어보기

지금 하는 일은 일부러 그래프에 고리를 만들어서 Terraform이 어떻게 막는지 보는 것입니다.

`compute.tf` 맨 아래에 SG 두 개를 서로 참조하도록 붙이고 `terraform plan`.

```hcl
resource "aws_security_group" "a" {
  vpc_id = aws_vpc.main.id
  ingress {
    from_port       = 0
    to_port         = 0
    protocol        = "-1"
    security_groups = [aws_security_group.b.id]   # a 가 b 를 기다림
  }
}
resource "aws_security_group" "b" {
  vpc_id = aws_vpc.main.id
  ingress {
    from_port       = 0
    to_port         = 0
    protocol        = "-1"
    security_groups = [aws_security_group.a.id]   # b 가 a 를 기다림 ← 고리 완성
  }
}
```

```
Error: Cycle: aws_security_group.a, aws_security_group.b
```

a는 b를 기다리고 b는 a를 기다립니다. 어느 쪽도 시작할 수 없습니다.

plan 단계에서 중단되므로 AWS에는 아무 일도 일어나지 않습니다. 해결 방법은 규칙을 `aws_vpc_security_group_ingress_rule`이라는 별도 리소스로 빼는 것입니다(개념워크북 13번).

> [!CAUTION]
> 확인했으면 이 블록을 반드시 지우세요.
>
> Cycle 에러는 그래프를 만드는 단계에서 나기 때문에 `plan`뿐 아니라 `destroy`도 실행되지 않습니다. 지우지 않고 Block C로 가면 destroy가 계속 실패하고 EC2가 계정에 남아 과금됩니다.
>
> 지운 뒤 `terraform plan`이 `No changes.`로 실행되는 것까지 확인하고 넘어가세요.

> [!WARNING]
> 블록 방식 `ingress`/`egress`와 별도 리소스 `aws_vpc_security_group_ingress_rule`을 섞어 쓰지 마세요. 두 방식이 서로의 규칙을 지웁니다.

### [실습] C-1. 삭제 순서를 먼저 예측하고 destroy plan 읽기

종이에 먼저 적어보세요. 의존성 지도를 뒤집으면 순서가 나옵니다.

```
[1단계] ___________________  ┃  ___________________
[2단계] ___________________  ┃  ___________________  ┃  ___________________
[3단계] ___________________
[4단계] ___________________
```

이제 정답을 확인합니다.

```bash

```

```

```

정답은 이렇습니다.

         (리프 노드. 아무도 이들을 참조하지 않음)

> [!IMPORTANT]
> 삭제 순서는 apply의 층 번호를 단순히 뒤집은 게 아닙니다. 의존 방향을 뒤집은 그래프에서 다시 계산합니다.

> 그래서 apply에서 3층이던 `instance`와 4층이던 `association`이 삭제에서는 같은 1단계가 됩니다. 둘 다 아무도 참조하지 않는 리프 노드라서 먼저 지울 수 있기 때문입니다.
>
> | | 기준 |
> |---|---|
> | apply | "**내가** 무엇을 기다리나" |
> | destroy | "**나를** 기다리는 게 아직 남아 있나" |
>
> 그리고 그 판단의 근거가 B-4에서 본 state의 `dependencies` 배열입니다.

> [!TIP]
> `terraform graph -type=plan-destroy`로도 볼 수 있지만, 이 출력은 기본 graph와 달리 `"[root] aws_subnet.public (expand)"` 처럼 복잡합니다. 보고 싶으면 이렇게 필터링해서 사용하세요(선택).
> ```bash
> terraform graph -type=plan-destroy \
>   | grep '\->' | grep -vE 'provider|output|root\] root' \
>   | sed 's/\[root\] //g; s/ (expand)//g; s/"//g; s/;//' | sort
> ```

### [함정] destroy가 실패할 때

> [!TIP]
> 먼저 이것부터 기억하세요. `destroy`는 몇 번을 실행해도 안전합니다. 이미 지워진 것은 건너뛰고 남은 것만 지웁니다. 실패했다고 당황해서 콘솔에서 직접 지우지 말고, 1~2분 기다렸다가 다시 실행하세요. 아래 에러의 대부분이 이 방법으로 해결됩니다.

> [!NOTE]
> 왜 기다리면 되는가. EC2에는 가상 네트워크 카드가 하나 붙어 있고(정식 명칭은 ENI, 네트워크 인터페이스), 이것이 서브넷의 IP 주소를 하나 사용 중입니다. 서버가 완전히 `terminated`가 되어야 이 네트워크 인터페이스가 해제되고, 그래야 서브넷과 SG를 지울 수 있습니다. 아래 `DependencyViolation` 에러들이 대부분 "아직 네트워크 인터페이스가 해제되지 않았다"는 뜻입니다.

| 에러 | 원인 | 해결 |
|------|------|------|
| `DependencyViolation: The subnet 'subnet-xxx' has dependencies and cannot be deleted` | 서버의 네트워크 카드가 아직 정리되지 않음 / 콘솔에서 직접 만든 리소스가 그 서브넷에 있음 | **1~2분 기다리고 `terraform destroy` 재실행.** 대부분 이걸로 끝납니다 |
| `DependencyViolation: Network vpc-xxx has some mapped public address(es)` | 퍼블릭 IP를 쓰는 리소스가 아직 남음 | 서버가 완전히 terminate될 때까지 대기 → 재실행 |
| `DependencyViolation: resource sg-xxx has a dependent object` | SG가 아직 서버에 붙어 있음 | 동일. B-6에서 SG `name`/`description`을 건드렸다면 먼저 원복 |
| `Error acquiring the state lock` | 다른 터미널에서 명령이 돌고 있거나 이전 실행이 비정상 종료됨 | 끝날 때까지 대기. 더 이상 사용되지 않는 잠금이면 `.terraform.tfstate.lock.info` 삭제 (Week3에서 `force-unlock` 다룹니다) |
| `Destroy complete! Resources: 6 destroyed.` (7이 아님) | 중간에 실패해서 일부만 삭제됨 | `terraform state list`로 남은 것 확인 → destroy 재실행 |

## 오늘의 명령 요약

의존성 지도 순서 그대로입니다.

```bash
curl -4 ifconfig.me                      # A-2  내 공인 IP
cp example.tfvars terraform.tfvars       # A-2  값 채우기
                                         # A-3~A-4 참조 ①~⑦ 잇기
terraform fmt && terraform init          # A-5
terraform validate                       # A-5  init 이후에
terraform plan                           # A-5  "5 to add"
terraform apply                          # A-6  네트워크 5개
terraform state list                     # A-6  7줄
terraform graph | grep '\->'             # A-7  그래프를 텍스트로
                                         # B-1  참조 ⑧~⑪ 잇기
terraform plan                           # B-2  "2 to add"
terraform apply                          # B-3  EC2 (30~60초, Ctrl+C 금지)
terraform state show aws_instance.web    # B-4  속성 확인
jq 'keys' terraform.tfstate              # B-4  최상위 키 7개
jq -r '.resources[] | .instances[0].dependencies' terraform.tfstate   # B-4 ⭐
terraform plan -refresh-only             # B-5  drift만 보기
terraform plan -destroy                  # C-1  삭제 순서 예측 채점
terraform graph -type=plan-destroy       # C-1  역방향 그래프
terraform destroy                        # C-2  7개 삭제. 필수!
terraform state list                     # C-3  빈 출력이어야 함
bash ../scripts/check-leftover.sh        # C-4  계정 잔존 0 확인
```

## 다음 주 예고

**Week 3. 원격 Backend & State 잠금.** 오늘 분석한 `terraform.tfstate`가 그대로 문제가 됩니다.

| 오늘 본 것 | Week3에서 |
|-----------|----------|
| state가 **내 노트북에만** 있다 | 팀원들은 이 state를 못 본다 → **S3 원격 저장소** |
| `serial`이 저장할 때마다 +1 | 두 명이 동시에 apply하면 충돌 → **잠금(lock)** |
| state가 평문 JSON | 원격에 두려면 **암호화·접근 제어** |
| `lineage`가 state의 고유 식별자 역할 | 잘못된 state를 덮어쓰는 사고를 어떻게 막나 |

예습: 원격 state가 왜 필요한지, `backend "s3"` 블록, `terraform init -migrate-state`
