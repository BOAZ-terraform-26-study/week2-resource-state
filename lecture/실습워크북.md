## 오늘의 지도 — 화살표 지도 (Arrow Map)

Week1의 지도는 **명령의 흐름**(Scope → Author → Initialize → Plan → Apply)이었습니다. 오늘의 지도는 **리소스 사이의 흐름**입니다. 이 지도를 한 세션에 세 번 씁니다 — Block A에서 **긋고**, Block B에서 apply 로그와 **대조하고**, Block C에서 **뒤집습니다.**

```
 레벨 0                레벨 1          레벨 2                   레벨 3                    레벨 4
                                    ┌─────────────────┐                          ┌──────────────────┐
 data.aws_             ┌──────────┐ │ subnet.public   │ ─⑥─────────────────────> │ route_table_     │
  availability ──②───> │ aws_vpc  │ ├─────────────────┤                          │  association     │
  _zones               │  .main   │ │ igw.gw          │    ┌──────────────────┐  │  .public         │
                       │          │ ├─────────────────┤    │ route_table      │ ─⑦────────────────>│
 data.aws_ami          └──────────┘ │ sg.web          │ ─⑤>│  .public         │  └──────────────────┘
  .al2023                           └─────────────────┘    ├──────────────────┤
                                                           │ instance.web     │
                       ①③⑧: vpc를 참조                 ⑨⑩⑪>└──────────────────┘
                       ④   : route_table -> vpc
```

**화살표 번호와 뜻은 개념워크북 1번 표와 같습니다.** 이 그림만 **"만들어지는 순서"** 방향(왼쪽 → 오른쪽)으로 그렸습니다. 실제 참조는 그 반대 방향입니다 — `subnet`이 `vpc`를 참조하므로, 코드와 `terraform graph`에서는 **`aws_subnet.public -> aws_vpc.main`**(= "subnet이 vpc를 기다린다")로 나옵니다.

| 스텝 | 여기서 긋는 화살표 | 하는 일 |
|------|------------------|--------|
| A-3 | ① ② | subnet 작성 |
| A-4 | ③ ④ ⑤ ⑥ ⑦ | IGW · route table · association 작성 |
| A-5 | — | plan — `Plan: 5 to add` |
| A-6 | — | **네트워크 5개 apply** |
| B-1 | ⑧ ⑨ ⑩ ⑪ | SG · EC2 작성 |
| B-2 | — | plan — `Plan: 2 to add` |
| B-3 | — | **컴퓨트 2개 apply** |
| C-1 · C-2 | 전부 **역방향** | **7개 destroy** (잎사귀부터) |

> [!NOTE]
> **지금 몇 번 화살표를 긋는 중인지**만 알면 길을 잃지 않습니다. 그리고 **화살표를 다 그으면 순서는 적지 않아도 됩니다.** 그게 오늘의 전부입니다.

> [!TIP]
> **레벨 4가 EC2가 아닙니다.** 인자가 참조 두 개뿐인 `route_table_association`이 가장 마지막입니다. 왜 그런지는 B-3에서 로그로 확인합니다.

**오늘 세 번 나오는 숫자를 미리 못 박아 둡니다.** 이것과 다르면 뭔가 잘못된 것입니다.

| 지점 | 숫자 |
|------|------|
| A-5 plan (네트워크만) | `Plan: 5 to add, 0 to change, 0 to destroy.` |
| A-6 후 `state list` | **7줄** (리소스 5 + 데이터 소스 2) |
| B-2 plan (EC2 추가) | `Plan: 2 to add, 0 to change, 0 to destroy.` |
| B-4 `state list` | **9줄** (리소스 7 + 데이터 소스 2) |
| C-1 destroy plan | `Plan: 0 to add, 0 to change, 7 to destroy.` |
| C-2 완료 | `Destroy complete! Resources: 7 destroyed.` |

### [실습] A-2. 내 값 채우기 — `project_name` · `my_ip`

```bash
cp example.tfvars terraform.tfvars
curl -4 ifconfig.me            # 내 공인 IPv4 한 줄이 나온다
```

`terraform.tfvars`를 열어 두 값을 바꿉니다.

```hcl
region       = "ap-northeast-2"
project_name = "boaz26-w2-{본인-github-id}"   # 예: boaz26-w2-kdh1834
my_ip        = "1.2.3.4"                      # curl -4 결과. /32 를 붙이지 말 것
instance_type = "t3.micro"
```

> [!IMPORTANT]
> **`my_ip`에 `/32`를 붙이지 마세요.** 코드가 `"${var.my_ip}/32"`로 조립합니다. `1.2.3.4/32`를 넣으면 `1.2.3.4/32/32`가 됩니다.
>
> `variables.tf`가 이걸 막아줍니다. 값이 `CHANGE-ME`거나 형식이 틀리면 **plan이 아예 시작되지 않습니다.**
>
> ```
> Error: Invalid value for variable
>   my_ip는 1.2.3.4 처럼 순수 IPv4여야 합니다. /32나 CIDR을 넣지 마세요.
> ```
>
> **이건 좋은 실패입니다.** 이 검사가 없으면 SG를 만드는 순간(apply 중간)에 `InvalidParameterValue`로 죽습니다. 그때는 VPC·subnet·IGW가 이미 만들어져 있어서 가장 당황하는 지점입니다.

> [!TIP]
> `curl`에 **`-4`를 꼭 붙이세요.** 안 붙이면 IPv6(`2001:...`)가 나올 수 있고, 그건 `/32`를 붙일 수 없는 값입니다.

> [!IMPORTANT]
> **CP1 — Discord에 `project_name` 한 줄만 올려주세요.** 오타를 apply 전에 걸러냅니다.

> [!CAUTION]
> **`my_ip` 값은 Discord에 올리지 마세요.** 본인 공인 IP입니다. `curl -4 ifconfig.me`가 IPv4 한 줄을 뱉었는지 **여부만**(`OK` / `실패`) 보고하세요.

### [실습] A-3. 첫 화살표 ① ② — subnet

`network.tf`의 첫 TODO입니다. `data "aws_availability_zones"`와 `aws_vpc.main`은 **이미 채워져 있습니다.**

```hcl
resource "aws_subnet" "public" {
  vpc_id            = aws_vpc.main.id                               # 화살표 ①
  cidr_block        = "10.0.1.0/24"
  availability_zone = data.aws_availability_zones.available.names[0] # 화살표 ②

  map_public_ip_on_launch = true

  tags = { Name = "${var.project_name}-public" }
}
```

**읽는 규칙은 하나입니다. 왼쪽은 인자 이름(provider가 정함), 오른쪽은 참조(내가 씀).**

```
vpc_id = aws_vpc.main.id
   ^          ^
   |          +--- 오른쪽: 내가 붙인 주소(aws_vpc.main) + 속성(.id)
   +-------------- 왼쪽: aws_subnet 이 요구하는 인자 이름
```

여기서 세 가지를 짚습니다.

**① `availability_zone`을 하드코딩하지 않습니다.** `"ap-northeast-2a"`라고 적으면 안 되는 이유는 두 개입니다.
- AZ 이름은 **계정마다 다른 물리 AZ에 매핑**됩니다. 오래된 계정은 특정 AZ에 서브넷을 못 만들 수도 있습니다.
- **AZ × 인스턴스 타입** 조합이 있습니다. `t3.micro`는 서울 4개 AZ 전부 가능하지만 **`t2.micro`는 2b·2d에 없습니다.**

**② `map_public_ip_on_launch = true` 한 줄이 퍼블릭 IP의 정체입니다.** 이 서브넷에서 뜨는 인스턴스는 퍼블릭 IPv4를 자동으로 받습니다. **그래서 우리는 Elastic IP를 만들지 않습니다.** EIP는 유휴 상태에서도 시간당 과금됩니다.

**③ 인터넷에 닿으려면 세 가지가 다 필요합니다.** 하나만 빠져도 조용히 안 됩니다.

```
① 주소가 있는가      : map_public_ip_on_launch = true            <- A-3
② 나가는 길이 있는가 : IGW + route table 0.0.0.0/0 + association <- A-4
③ 방화벽이 허용하는가: SG egress 전체 허용                        <- B-1
```

### [실습] A-4. 화살표 ③ ④ ⑤ ⑥ ⑦ — IGW · route table · association

`network.tf`의 남은 TODO 3개를 채웁니다.

```hcl
resource "aws_internet_gateway" "gw" {
  vpc_id = aws_vpc.main.id # 화살표 ③
  tags   = { Name = "${var.project_name}-igw" }
}

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id # 화살표 ④

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.gw.id # 화살표 ⑤
  }

  tags = { Name = "${var.project_name}-rt-public" }
}

resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id      # 화살표 ⑥
  route_table_id = aws_route_table.public.id # 화살표 ⑦
}
```

그리고 `outputs.tf`의 첫 TODO도 지금 채웁니다.

```hcl
output "vpc_id" {
  description = "생성된 VPC ID"
  value       = aws_vpc.main.id
}
output "subnet_id" {
  description = "퍼블릭 서브넷 ID"
  value       = aws_subnet.public.id
}
output "subnet_az" {
  description = "서브넷이 놓인 AZ — data.aws_availability_zones 가 골라준 값"
  value       = aws_subnet.public.availability_zone
}
```

여기서 볼 것이 두 개입니다.

**`route`는 리소스가 아니라 인자입니다.** `resource "aws_route_table"` 안에 중괄호로 들어간 `route { }`는 별개의 리소스가 아니라 **라우트 테이블의 속성**입니다. 겉모습이 `resource` 블록과 비슷해서 헷갈리기 쉽습니다. 이렇게 안에 들어가는 것을 **인라인 블록**이라고 부릅니다.

**`association`은 "연결 자체가 리소스"입니다.** AWS 콘솔에는 이걸 위한 독립 화면이 없습니다(라우트 테이블 화면의 탭으로 보입니다). 그런데 Terraform에서는 리소스 하나이고, **인자가 참조 두 개뿐**입니다. 그래서 화살표 지도에서 **가장 마지막 레벨**입니다.

### [확인] subnet 블록 — 확정된 값과 아직 모르는 값

```
  # aws_subnet.public will be created
  + resource "aws_subnet" "public" {
      + availability_zone                              = "ap-northeast-2a"
      + availability_zone_id                           = (known after apply)
      + cidr_block                                     = "10.0.1.0/24"
      + id                                             = (known after apply)
      + map_public_ip_on_launch                        = true
      + tags                                           = {
          + "Name" = "boaz26-w2-kdh1834-public"
        }
      + tags_all                                       = {
          + "ManagedBy" = "terraform"
          + "Name"      = "boaz26-w2-kdh1834-public"
          + "Project"   = "boaz26-w2-kdh1834"
          + "Study"     = "boaz-terraform-26"
          + "Week"      = "2"
        }
      + vpc_id                                         = (known after apply)
    }
```

**세 줄을 나란히 보세요. 이게 오늘의 핵심입니다.**

| 줄 | 값 | 왜 |
|----|----|----|
| `cidr_block` | `"10.0.1.0/24"` | **내가 직접 적은 값**이라 plan 때 이미 안다 |
| `availability_zone` | `"ap-northeast-2a"` | **데이터 소스가 읽어온 값**이라 plan 때 이미 안다 |
| `vpc_id` | `(known after apply)` | **VPC를 만들어야 정해지는 값** → 화살표 ①의 정체 |

**`(known after apply)`가 화살표의 증거입니다.** "값을 아직 모른다"가 곧 "그것보다 나중에 만들어야 한다"입니다.

그리고 `tags`와 `tags_all`을 비교하세요. **`tags`는 내가 쓴 것(`Name` 1개), `tags_all`은 `providers.tf`의 `default_tags`와 병합된 최종 결과(5개)** 입니다. 내가 이 리소스에 쓰지 않은 태그 **4개**(`Project`·`Study`·`Week`·`ManagedBy`)가 자동으로 붙었습니다.

```
Plan: 5 to add, 0 to change, 0 to destroy.

Changes to Outputs:
  + subnet_az = "ap-northeast-2a"
  + subnet_id = (known after apply)
  + vpc_id    = (known after apply)
```

> [!IMPORTANT]
> **`Plan: 5 to add`가 아니면 멈추세요.** 4면 TODO가 덜 채워졌고, 7이면 `compute.tf`의 TODO를 미리 채운 것입니다(그것도 괜찮지만 A-6의 로그 관찰이 흐려집니다).

### [함정] plan이 멈추거나 이상할 때

| 증상 | 원인 | 해결 |
|------|------|------|
| `my_ip는 1.2.3.4 처럼...` 에러 | `terraform.tfvars`가 `CHANGE-ME` 그대로 | A-2를 다시 |
| `var.project_name` 을 입력하라며 멈춤 | `terraform.tfvars`를 안 만듦 | **Ctrl+C로 빠져나오고** 파일부터 만들 것. 아무거나 치면 그 값으로 apply된다 |
| `No changes.` | TODO가 아직 주석 상태 | 주석을 풀고 채우기 |
| `Reference to undeclared resource` | 주소 오타 (`aws_vpc.main` ↔ `aws_vpc.mian`) | `validate`가 줄 번호를 알려준다 |
| `Inconsistent dependency lock file` | `init`을 안 함 | `terraform init` |
| `Your query returned no results` | AMI 필터가 아무것도 못 잡음 | 리전이 `ap-northeast-2`인지 확인 |

>
> 그런데 왜 state에 또 적어둘까요? **`.tf` 파일을 다 지워도 `terraform destroy`가 올바른 순서로 동작해야 하기 때문**입니다. 코드가 사라지면 참조도 사라지지만, 장부의 `dependencies`는 남습니다. C-2의 삭제 순서가 지켜지는 근거가 이것입니다.
>
> **나는 이 배열을 적은 적이 없습니다.** 화살표 ①~⑪에서 자동으로 뽑혀 여기 적혔습니다.

> [!NOTE]
> `dependencies`에는 직접 의존 외에 **간접(전이) 의존까지** 들어갑니다(association에 `aws_vpc.main`이 함께 보이는 이유). 그래프 간선 수와 정확히 1:1은 아닙니다.
>
> 그리고 **`aws_instance.web`의 목록에 `aws_route_table_association.public`은 없습니다.** EC2는 라우트가 붙기를 기다리지 않습니다 — 참조가 없으니까요. 오늘은 문제가 안 되지만, `user_data`로 패키지를 받는다면 **인터넷이 아직 없어서 실패하는 경쟁 상태**가 됩니다. 그때 필요한 것이 `depends_on`입니다(개념워크북 6번).

### [실습] B-6 (심화 ⭐). `~` vs `-/+` 체험 — **plan만, apply 금지**

> [!WARNING]
> **이 스텝에서는 절대 `apply`를 누르지 마세요.** plan만 보고 즉시 원복합니다. apply하면 EC2가 죽고 새로 만들어집니다(시간 + 과금).

#### 대조군 — `instance_type`은 `~`

`terraform.tfvars`에서 `instance_type = "t2.micro"`로 바꾸고 plan.

```
  # aws_instance.web will be updated in-place
  ~ resource "aws_instance" "web" {
        id            = "i-0123456789abcdef0"
      ~ instance_type = "t3.micro" -> "t2.micro"
    }

Plan: 0 to add, 1 to change, 0 to destroy.
```

EC2에는 `ModifyInstanceAttribute` API가 있어 **중지 → 변경 → 시작**으로 처리됩니다. 인스턴스 ID가 유지되므로 `~`입니다. **하지만 다운타임은 있습니다** — `~`가 곧 무해는 아닙니다.

#### 본 실습 — subnet `cidr_block`은 `-/+`, 그리고 **연쇄**

`network.tf`에서 `cidr_block = "10.0.1.0/24"` → `"10.0.2.0/24"` (한 글자) 후 plan.

```
Resource actions are indicated with the following symbols:
-/+ destroy and then create replacement

  # aws_instance.web must be replaced
-/+ resource "aws_instance" "web" {
      ~ subnet_id = "subnet-0a1b2c3d4e5f67890" -> (known after apply) # forces replacement
    }

  # aws_route_table_association.public must be replaced
-/+ resource "aws_route_table_association" "public" {
      ~ subnet_id = "subnet-0a1b2c3d4e5f67890" -> (known after apply) # forces replacement
    }

  # aws_subnet.public must be replaced
-/+ resource "aws_subnet" "public" {
      ~ cidr_block = "10.0.1.0/24" -> "10.0.2.0/24" # forces replacement
    }

Plan: 3 to add, 0 to change, 3 to destroy.
```

**세 가지를 읽으세요.**

**① `# forces replacement` 주석의 위치** — 리소스 헤더가 아니라 **원인이 된 속성 줄의 맨 끝**입니다. 그 속성이 범인입니다.
**② 연쇄** — 한 줄 고쳤는데 **3개가 재생성**됩니다. 서브넷이 죽으면 그 `id`를 참조한 association과 EC2도 같이 죽습니다. **화살표 지도가 곧 교체 전파 경로**입니다.
**③ `(known after apply)`의 재등장** — "새 서브넷의 id를 아직 모른다 → 그걸 참조하는 인스턴스를 새로 만들어야 한다"는 인과가 이 한 줄에 다 들어 있습니다.

**apply를 누르면 EC2가 죽고 퍼블릭 IP가 바뀝니다. 운영 중이라면 장애입니다.**

#### 반드시 원복

> [!CAUTION]
> **`git checkout -- network.tf` / `git restore network.tf` 를 쓰지 마세요.** `practice/network.tf`는 리포에 **TODO 주석 스켈레톤 상태로 커밋돼 있습니다.** git으로 되돌리면 cidr 한 글자가 아니라 **A-3·A-4에서 채운 코드 전부가 사라집니다.** 그러면 다음 `plan`이 `No changes.`가 아니라 `5 to destroy`로 나옵니다.

**손으로 되돌립니다.**

```bash

# 2) terraform.tfvars 의 instance_type 을 "t3.micro" 로 직접 수정
git diff practice/network.tf   # 스켈레톤과의 차이 = 내가 채운 코드. cidr가 10.0.1.0/24 인지 확인
```

| `Error acquiring the state lock` | 다른 터미널의 명령이 돌고 있거나 이전 실행이 비정상 종료 | 끝날 때까지 대기. 진짜 죽은 락이면 `.terraform.tfstate.lock.info` 삭제 (Week3에서 `force-unlock` 다룸) |
| `Destroy complete! Resources: 6 destroyed.` (7이 아님) | 중간 실패로 부분 삭제 | `terraform state list`로 남은 것 확인 → destroy 재실행 |

### [실습] C-4. 계정 잔존 점검 — **"state가 비었다 ≠ 계정이 비었다"**

콘솔 우측 상단이 **서울(ap-northeast-2)** 인지 먼저 확인하세요. 리전이 다르면 아무것도 안 보이는 게 당연합니다.

| 확인할 것 | 콘솔 경로 | 정상 |
|----------|----------|------|
| EC2 인스턴스 | EC2 → Instances | `terminated`만 (`running`/`stopped`는 사고) |
| **EBS 볼륨** | EC2 → Volumes | `available` 상태인 볼륨 **0개** |
| **Elastic IP** | EC2 → Elastic IPs | **0개** |
| **NAT Gateway** | VPC → NAT Gateways | **0개** |
| ENI | VPC → Network Interfaces | 내 VPC의 것 없음 |

화살표 지도 순서 그대로입니다.

```bash
curl -4 ifconfig.me                      # A-2  내 공인 IP

                                         # A-3~A-4 화살표 ①~⑦ 긋기

terraform validate                       # A-5  init 이후에
terraform plan                           # A-5  "5 to add"
terraform apply                          # A-6  네트워크 5개
terraform state list                     # A-6  7줄
terraform graph | grep '\->'             # A-7  그래프를 텍스트로
                                         # B-1  화살표 ⑧~⑪ 긋기
terraform plan                           # B-2  "2 to add"
terraform apply                          # B-3  EC2 (30~60초, Ctrl+C 금지)
terraform state show aws_instance.web    # B-4  속성 파보기
jq 'keys' terraform.tfstate              # B-4  최상위 키 7개
jq -r '.resources[] | .instances[0].dependencies' terraform.tfstate   # B-4 ⭐
terraform plan -refresh-only             # B-5  drift만 보기
terraform plan -destroy                  # C-1  삭제 순서 예측 채점
terraform graph -type=plan-destroy       # C-1  역방향 그래프
terraform destroy                        # C-2  7개 삭제 — 필수!
terraform state list                     # C-3  빈 출력이어야 함
bash ../scripts/check-leftover.sh             # C-4  계정 잔존 0 확인
```
